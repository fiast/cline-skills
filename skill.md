## ⛔ ПРАВИЛА БЕЗОПАСНОСТИ (читать первыми, нарушать запрещено)

### Режим по умолчанию: READ-ONLY

**Скилл работает в режиме «наблюдатель».** По умолчанию разрешено **только**:

- чтение метрик (`top`, `free`, `iostat`, `ss`, `vmstat`, `uptime`, `dmesg`, `df`, `ip -s link`, `nstat`, `pidstat`, `mpstat`, `pmap`, `atop -r`, `cat /proc/*`, `cat /sys/*`);
- анализ и формирование отчёта;
- вывод рекомендаций пользователю.

### 🚫 ЗАПРЕЩЕНО выполнять БЕЗ ЯВНОГО РАЗРЕШЕНИЯ пользователя

Следующие команды **НЕ выполняются автоматически**, даже если они кажутся «логичным следующим шагом». Перед запуском скилл **обязан**:

1. Объяснить, **зачем** это нужно.
2. Показать **точную команду**, которая будет выполнена.
3. Описать **последствия** (что может сломаться / замедлиться).
4. **Дождаться явного "да"** от пользователя в чате.

**Список команд, требующих подтверждения:**

| Категория | Команды | Почему опасно |
|---|---|---|
| **Убийство процессов** | `kill`, `kill -9`, `pkill`, `killall`, `systemctl stop/restart` | Потеря данных, падение сервиса |
| **Изменение ядра** | `sysctl -w`, `echo ... > /proc/sys/*`, `echo ... > /sys/*` | Мгновенно влияет на всю систему, риск потери сети/диска |
| **Приоритеты** | `renice`, `nice`, `ionice`, `taskset`, `chrt` | Может «задушить» или «разогнать» процессы непредсказуемо |
| **Запись на диск** | `rm`, `mv`, `truncate`, `dd`, `> file` | Необратимая потеря данных |
| **Управление сервисами** | `systemctl`, `service`, `mount`, `umount` | Отключение сервисов, потеря доступа |
| **Сеть** | `iptables`, `nft`, `ip link set`, `ifconfig down` | Потеря SSH-доступа к серверу |
| **Пакеты** | `apt install`, `yum install`, `pip install` | Изменение окружения |
| **Тяжёлые трейсеры** | `strace` (без фильтров/без ограничения по времени), `perf record`, `tcpdump -w` | Overhead 10–100x, замедление прода, забивание диска |
| **Планировщики** | `echo ... > /sys/block/*/queue/scheduler` | Влияет на все I/O |
| **Своп** | `swapon`, `swapoff`, `mkswap` | Может обрушить систему при нехватке RAM |

### ✅ Что делать, если для диагностики нужна «опасная» команда

Алгоритм:

1. Завершить **read-only** часть диагностики.
2. В отчёте сформулировать **гипотезу** и **предлагаемое действие**.
3. Явно попросить разрешение, например:

   > **Требуется ваше разрешение.**
   >
   > **Команда:** `sudo renice -n 19 -p 12345`
   > **Зачем:** понизить приоритет процесса бэкапа, который монополизирует диск (`%util=100%`, `w_await=250ms`).
   > **Риск:** бэкап будет идти дольше; критичных последствий нет, откат — `renice -n 0 -p 12345`.
   > **Подтвердите, пожалуйста, запуск (да/нет).**

4. Ждать ответа. **Молчание = запрет.**
5. Если пользователь разрешил — выполнить, зафиксировать метрики до/после.
6. Если пользователь запретил или не ответил — оставить рекомендацию в отчёте как «требует действий вручную».

### Что можно делать без спроса (явный whitelist)

```text
uptime, hostname, uname, nproc
free, vmstat, top -bn1, mpstat, pidstat, pmap, slabtop
df, du (без удаления), iostat, iotop -b -n <N> (короткий прогон)
dmesg, journalctl (только чтение), cat /proc/*, cat /sys/*
ss, ip -s link, ip a, nstat -az, iftop (короткий прогон), mtr (короткий)
atop -r (чтение логов)
strace -c -p PID (только с фильтром и ≤ 30 сек, с предупреждением)
ab (только на localhost, короткий прогон)
```

Даже для этих команд — **короткие прогоны** и **предупреждение** пользователя, если это продакшен.

## Когда использовать

- Пользователь просит подключиться к серверу и провести диагностику.
- Жалобы на «сервер тормозит», «высокий load average», «утечка памяти», «диск забит», «сеть лагает».
- Требуется health check / post-mortem инцидента.

---

## Ключевые принципы (запомнить навсегда)

1. **Load Average — это очередь, а не проценты.** Сравнивать с числом ядер (`nproc`).
2. **Контекст решает всё.** LA=10 на 1 ядре — катастрофа, на 12 ядрах — норма.
3. **Не вся нагрузка одинакова:**
   - `us` (User) — полезная работа.
   - `sy` (System) — паразитные syscalls.
   - `wa` (I/O Wait) — CPU ждёт диск.
   - `si` (Soft IRQ) — сетевые штормы.
4. **Free RAM is wasted RAM.** Смотреть `available`, а не `free`. `buff/cache` — это хорошо.
5. **VIRT — иллюзия, RES — реальность.**
6. **Swap — аварийный карман, не расширение RAM.**
7. **Состояние D — «тихий убийца».** Процесс в D нельзя убить `kill -9`, нужно чинить I/O.
8. **Диск: latency (`await`) важнее скорости в МБ/с.**
9. **Data-driven:** любое действие обосновано метрикой. Никаких догадок.
10. **strace создаёт overhead 10–100x.** Использовать только с фильтрами и на 10–30 сек.

## USE-метод (каркас диагностики каждого ресурса)

Для каждого ресурса ответить на три вопроса:

- **U**tilization — насколько ресурс занят (0–100%)?
- **S**aturation — есть ли очередь желающих получить ресурс?
- **E**rrors — есть ли явные ошибки?

## Шаг 1. General Health Check (60 секунд)

Выполнить одной пачкой — это «анамнез»:

```bash
echo "=== UPTIME / LOAD ==="; uptime
echo "=== CPU CORES ==="; nproc
echo "=== FREE RAM ==="; free -h
echo "=== DISK SPACE ==="; df -h
echo "=== DMESG (последние ошибки) ==="; dmesg -T | tail -20
```

### Матрица интерпретации

| Симптом | Косвенный признак | Гипотеза | Дальше смотреть |
|---|---|---|---|
| High load average | `id` ≈ 0% в top | CPU bound | Шаг 2 (CPU) |
| High load average | `wa` высокий | I/O bound | Шаг 4 (Disk) |
| OOM Killer в dmesg | `available` ≈ 0 | Memory leak | Шаг 3 (RAM) |
| Диск 90%+ | ошибки записи | Disk space | Шаг 4 (Disk) |

## Шаг 2. Диагностика CPU

### 2.1. Структура загрузки

```bash
top -bn1 | head -20
# Смотрим строку %Cpu(s): us, sy, wa, si, id
```

### 2.2. Load average и тренд

```bash
uptime
# LA < nproc → ок. LA > nproc и растёт (3→5→8) → расследование
```

### 2.3. Кто нагружает

```bash
top -bn1 -o %CPU | head -20
# или
pidstat -u 1 5
```

### 2.4. По ядрам (дисбаланс)

```bash
mpstat -P ALL 1 3
```

### 2.5. Контекстные переключения (шторм?)

```bash
vmstat 1 5   # колонки: r (очередь), cs (context switches), in (interrupts)
```

### Диагноз и лечение

| Метрика | Диагноз | Решение |
|---|---|---|
| Высокий `us` | Приложение честно работает | Оптимизация кода, профилирование, масштабирование |
| Высокий `sy` | Частые syscalls | `strace -c -p PID`, проверка драйверов |
| Высокий `wa` | CPU ждёт диск | → Шаг 4 |
| Высокий `si` | Сетевой шторм | → Шаг 5 (pps, настройка NIC) |
| Процесс в состоянии **D** | Uninterruptible Sleep, ждёт I/O | Не убивать! Чинить I/O (Шаг 4) |
| Процесс в состоянии **Z** | Zombie | Найти родителя: `pstree -p PID`, разобраться с родителем |

## Шаг 3. Диагностика RAM

### 3.1. Общая картина

```bash
free -h
# Смотреть available, не free! Если available < 10-20% — память под вопросом
```

### 3.2. Своппинг в динамике

```bash
vmstat 1 5
# Колонки si / so: нули — ок; бегут → thrashing
```

### 3.3. Виновник

```bash
top -bn1 -o %MEM | head -20
# или в интерактиве: Shift+M (сортировка по RES)
```

### 3.4. OOM Killer — история

```bash
dmesg -T | grep -iE "killed process|out of memory"
```

### 3.5. Глубокий анализ (если процесс найден)

```bash
pmap -x <PID> | tail -20   # искать утечки в [ anon ]
```

### Диагноз и лечение

| Признак | Диагноз | Решение |
|---|---|---|
| OOM в dmesg + available ≈ 0 | Утечка памяти | Изолировать через systemd `MemoryMax` (cgroup), не просто рестарт |
| `si`/`so` ненулевые в vmstat | Thrashing | Оптимизация софта или докупка RAM |
| VIRT огромный, RES маленький | Норма (Java/Go резервируют) | Не пугаться |
| Process в D из-за swap | Swap нагружает диск | Лечить память, а не диск |

### Cheat sheet тюнинга памяти (для DB-серверов)

| Параметр | Desktop | DB server |
|---|---|---|
| `vm.swappiness` | 60 | 1–10 |
| `vm.dirty_ratio` | 20 | 10 |
| `vm.dirty_background_ratio` | 10 | 5 |
| `vm.vfs_cache_pressure` | 100 | 100 (50 для файловых серверов) |
| Transparent Huge Pages | always | never |

> ⚠️ **Применение этих параметров = `sysctl -w` → требует подтверждения пользователя.**

## Шаг 4. Диагностика дисковой подсистемы

### 4.1. Утилизация и latency

```bash
iostat -xkz 1 3
# Игнорировать первый блок (это среднее с загрузки)
# r_await / w_await — latency. Для SSD: <1-5 мс = ок, >10-20 мс и растёт = bottleneck
# %util — утилизация
# avgqu-sz — размер очереди
```

### 4.2. Кто пишет/читает

```bash
sudo iotop -o -b -n 3
# Смотреть IO%, DISK READ/WRITE, SWAPIN
# Если SWAPIN > 0 — проблема в RAM, а не в диске
```

### 4.3. Процессы (альтернатива)

```bash
pidstat -d 1 5
# Колонка kB_rd/s, kB_wr/s
```

### 4.4. Ошибки диска

```bash
dmesg -T | grep -iE "I/O error|ata|nvme|sd"
```

### Алгоритм диагностики одним взглядом

| Шаг | Условие | Интерпретация | Что делать |
|---|---|---|---|
| 1. `iostat -xkz` | await, avgqu-sz высокие/растут | Диск — bottleneck | → шаг 3 |
| | Метрики в норме | Проблема не в диске | → шаг 2 |
| 2. `%util` | Низкий | Штатная работа | Готово |
| | ≈100% | SSD: норма; HDD: предел | Для HDD копать глубже |
| 3. `iotop -o` | SWAPIN > 0 | Нехватка RAM | Лечить память! |
| | Высокий IO% | Виновник найден | Сверить DISK READ/WRITE |

### Быстрая таблица диагнозов

| Симптом | Причина | Что делать |
|---|---|---|
| Мало МБ/с, высокий await | IOPS-bottleneck (random) | NVMe, кэш, укрупнение операций |
| %util≈100%, await низкий | Норма для SSD; предел HDD | Для HDD — копать |
| SWAPIN > 0% в iotop | Paging | Лечить RAM |
| Высокий await, %util низкий (облако) | Throttling провайдера | Проверить лимиты IOPS |
| Высокий await + растёт avgqu-sz | Очередь переполнена | Увеличить IOPS или параллелизм |

### Планировщик I/O — рекомендации

| Устройство | Сценарий | Планировщик |
|---|---|---|
| HDD | БД / файловый сервер | `mq-deadline` |
| HDD | Desktop | `bfq` |
| SSD/NVMe | Высокопроизв. БД | `none` |
| SSD/NVMe | Смешанная нагрузка, latency | `kyber` |
| VM (Guest) | — | `none`/`noop` |

Проверить (можно без спроса):

```bash
cat /sys/block/sda/queue/scheduler
```

Сменить (⚠️ **только с подтверждением!**):

```bash
# echo mq-deadline | sudo tee /sys/block/sda/queue/scheduler
```

## Шаг 5. Диагностика сети

### 5.1. Физика / канальный уровень

```bash
ip -s link
# Смотреть errors (битый кабель) и dropped/overrun (переполнение буфера NIC)
```

### 5.2. Утилизация канала

```bash
sudo iftop -n -N -i eth0
# Total rates близки к физическому лимиту → канал забит
# Найти конкретные IP
```

### 5.3. Сокеты и очереди приложения

```bash
ss -tulpn                          # слушающие
ss -nt state established           # активные
# Recv-Q > 0 → приложение не успевает читать
# Send-Q > 0 → сеть не успевает отправлять
```

### 5.4. Аномалии TCP-состояний

```bash
ss -s
# Тысячи CLOSE-WAIT → баг приложения (не закрывает сокеты)
# Десятки тысяч TIME-WAIT → риск исчерпания портов
```

### 5.5. Дропы на уровне ядра

```bash
nstat -az | grep -iE "drop|overflow|listen"
# ListenOverflows / ListenDrops → переполнение accept-очереди
```

### Чек-лист траблшутинга сети

1. Есть дропы на интерфейсе? → `ip -s link` (dropped, overrun)
2. Забит ли канал? → `iftop` (Total rates ≈ лимит)
3. Очереди на сокетах? → `ss` (Recv-Q > 0)
4. Аномалии TCP? → `ss -s` (CLOSE-WAIT, TIME-WAIT)

### Тюнинг TCP/IP (⚠️ **только с подтверждением!**)

- **Backlog:** `net.core.somaxconn` + `listen backlog` в Nginx (используется минимум из двух).
- **SYN queue:** `net.ipv4.tcp_max_syn_backlog`.
- **Эфемерные порты:** `net.ipv4.ip_local_port_range`.
- **TIME_WAIT reuse:** `net.ipv4.tcp_tw_reuse`.
- **BBR:** `net.ipv4.tcp_congestion_control=bbr`.

> **Правила:**
> - `tcp_tw_recycle` — УДАЛЁН из ядра, ломает NAT. НЕ использовать.
> - Считайте бюджет памяти: буферы × соединения.
> - Любое изменение — после метрики. Сначала `nstat` показал дропы — потом увеличили.
> - **Каждый `sysctl -w` — отдельный запрос разрешения у пользователя.**

## Шаг 6. История (atop) — если «тормозило вчера»

```bash
atop -r              # лог за сегодня
atop -r y            # за вчера
atop -r /var/log/atop/atop_YYYYMMDD
```

**Навигация:**

- `t` / `T` — вперёд/назад на интервал
- `b` — к конкретному времени (HH:MM)
- `r` — в начало файла

**Сортировка:**

- `c` — по CPU (SYSCPU, USRCPU)
- `m` — по Memory (RGROW/VGROW — утечки!)
- `d` — по Disk
- `n` — по Network
- `a` — auto (по самому нагруженному ресурсу)

**Вид:**

- `g` — общий вид
- `1` — по каждому ядру
- `v` — verbose (PPID, User, время старта)
- `y` — потоки
- `q` — выход

## Шаг 7. Трассировка системных вызовов (strace)

**Когда:** все метрики в норме, но приложение тормозит — оно чего-то ждёт.

⚠️ **Требует предупреждения пользователя даже в read-only виде** — overhead 10–100x.

```bash
# Подключиться к процессу, только сетевые вызовы, с временем
sudo strace -p <PID> -T -e trace=network

# Или файловые
sudo strace -p <PID> -T -e trace=file

# Статистика за 10-15 сек
sudo strace -c -p <PID>
```

**Что искать:**

- `connect()` к DNS (порт 53) висит 5 сек → мёртвый nameserver в `/etc/resolv.conf`.
- Бесконечные `futex(FUTEX_WAIT)` → deadlock на мьютексе.
- `connect()` к внешнему API не отвечает → проблема у зависимости.
- `openat(...) = -1 ENOENT` → файла нет там, где его ищут.

> **Безопасность:** overhead 10–100x. Только с фильтрами `-e`, на 10–30 секунд.
> **Альтернативы на проде:** `perf`, `eBPF`.

## Тюнинг приоритетов (⚠️ **только с подтверждением!**)

**НЕ убивать бэкапы!** Понижать приоритет:

```bash
# CPU
renice -n 19 -p <PID>

# Disk I/O
ionice -c 3 -p <PID>
```

**CPU affinity (только для специфичных нагрузок):**

- Redis/Memcached, Nginx/HAProxy/DPDK, ScyllaDB — да.
- Не использовать «на всякий случай».
- Всегда сравнивать «до/после».

```bash
taskset -c 0,1 -p <PID>
```

**NUMA:** при привязке к ядрам одного сокета — убедиться, что память тоже локальна.

**Осторожно с NI = -20:** может заблокировать SSH. Использовать -10/-15.

## Финальный чек-лист диагностики (USE Method)

### CPU

- **Utilization:** `top` (us, sy, id)
- **Saturation:** `uptime` (LA > nproc), `vmstat 1` (колонка `r`)
- **Errors:** `dmesg` (throttling, overheating)
- **Tools:** `uptime`, `top`, `mpstat -P ALL`, `pidstat`

### RAM

- **Utilization:** `free -h` (available)
- **Saturation:** `vmstat 1` (si/so)
- **Errors:** `dmesg | grep -i "Out of memory"`
- **Tools:** `free`, `vmstat`, `pmap`, `slabtop`

### Storage

- **Utilization:** `iostat -xz 1` (%util)
- **Saturation:** `iostat -xz 1` (avgqu-sz, await)
- **Errors:** `dmesg` (I/O errors), `smartctl`
- **Tools:** `iostat`, `iotop`, `pidstat -d`

### Network

- **Utilization:** `ip -s link`, `iftop`
- **Saturation:** `ss -s`, `nstat -az`
- **Errors:** `ip -s link` (errors, dropped)
- **Tools:** `ss`, `ip`, `tcpdump`, `mtr`

## Правила поведения скилла

### 🔴 Обязательные (нарушение = критическая ошибка)

1. **Работать в read-only по умолчанию.** Сбор метрик и отчёт — без вопросов.
2. **Любое действие из «списка запрещённых» — только после явного подтверждения пользователя.**
   Формат запроса:
   > **Команда:** `<точная команда>`
   > **Зачем:** `<обоснование метрикой>`
   > **Риск:** `<что может пойти не так>`
   > **Откат:** `<как вернуть как было>`
   > **Подтвердите запуск (да/нет).**
3. **Молчание = запрет.** Не выполнять «по умолчанию», не додумывать за пользователя.
4. **Не убивать процессы без анализа.** Процесс в D — не убивается вообще.
5. **Не запускать тяжёлые инструменты (`strace`, `iotop`, `perf`) без предупреждения** на продакшене.
6. **Каждое действие — с обоснованием метрикой.**
7. **Формировать итоговый отчёт** в формате: Проблема → Root Cause → Действия → Результат (метрики до/после).
8. **Задавать уточняющие вопросы**, если данных недостаточно.

### 🟡 Рекомендательные

2. **Различать симптом и причину:** `wa` высокий — симптом, причина — конкретный процесс или своппинг.

## Шаблон запроса разрешения

Когда скилл решает, что нужен «опасный» шаг, он **обязан** вывести такое сообщение и **остановиться**:

```
⚠️ ТРЕБУЕТСЯ РАЗРЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ

Команда:      sudo ionice -c 3 -p 14872
Зачем:        Процесс backup.sh (PID 14872) создаёт 80 МБ/с записи,
              из-за чего w_await вырос до 250 мс, а %util = 100%.
              Понижение I/O-приоритета разгрузит диск.
Риск:         Бэкап будет идти дольше. Критичных последствий нет.
              Сервис не затрагивается.
Откат:        sudo ionice -c 2 -p 14872
Ожидаемый эффект: w_await ↓ до <10 мс, отзывчивость БД восстановится.

Подтвердите запуск: (да / нет / другое)
```

Пока пользователь не ответил явно — **скилл ожидает и не выполняет команду**.

## Философия

> Учите принципы, а не флаги. Флаги есть в `man`. Понимайте, *почему* растёт LA, как работает page cache и зачем нужны syscalls. Оператор знает флаги `top`. Эксперт понимает, как CFS распределяет кванты времени.
>
> Инженер, который вносит изменения на продакшене без подтверждения, — не инженер, а угроза. **Сначала наблюдай, потом спрашивай, потом меняй.**
